# Qor — заказы поставщикам для ekt.kz

**Qor** (қаз. *қор* — запас). Сервис для менеджера закупа ТОО «Электрокомплект»: по выгрузке из 1С считает, что пополнить на складе, в каком количестве и насколько срочно.

Сейчас это делают вручную в Excel и редко. Из-за этого по одним позициям копится лишний запас, по другим возникает дефицит, а разовая крупная отгрузка искажает регулярную потребность. Qor собирает рекомендацию по каждому артикулу и не отправляет заказ поставщику сам: человек проверяет количество и отдельным шагом утверждает.

Два клиента, один расчёт:

- **Сайт** — рабочее место закупщика: загрузка выгрузки, таблица заказов, правка количества, карточка артикула с шагами расчёта.
- **Телефон** — согласование. Руководитель видит тот же заказ, спрашивает «почему столько» и нажимает «Утвердить» или «Вернуть». Поставщику ничего не уходит: после утверждения менеджер выгружает заказ в 1С на сайте.

## Как считается заказ

Рабочий расчёт — `backend/qor/pipeline.py`. Он читает Excel, строит те же признаки, что при обучении, и прогоняет модель `ml/models/demand_model.cbm` (CatBoost, цель — продажи следующего месяца).

На каждый артикул:

```
рекомендация = прогноз + 0,5 × σ за 6 месяцев − остаток − в пути
```

Результат округляется вверх до минимальной партии (MOQ). Срочность — покрытие остатком и товаром в пути: меньше 0,5 месяца спроса — «Критично», меньше 1 — «Скоро», иначе «Норма». У каждой строки есть шаги: прогноз, страховой запас, остаток, в пути, округление.

Признаки модели: лаги продаж 1/2/3/6/12, скользящие среднее и σ, рост за 3 месяца, остаток, календарь (`month_sin` / `month_cos`, квартал) и флаг пустого остатка. Клиентов в расчёте нет: в выгрузке нет персонального идентификатора, крупную отгрузку можно увидеть только по номеру документа.

Обучение с поправкой на выбросы и пустые месяцы — отдельный контур, `scripts/prepare_dataset_v2.py` и `ml/models/demand_model_v2.cbm`:

- **Разовая крупная продажа.** По каждому артикулу порог = скользящая медиана за 6 месяцев + 6 × MAD. Если MAD равен нулю, порог = max(4 × медиана, медиана + 10). Месяц выше порога заменяется медианой и не входит в регулярный спрос.
- **Упущенный спрос.** Месяц без остатка не считается нулевым спросом: оценка потерянных продаж добавляется к очищенному ряду (`demand_adjusted`).

Заказы для сайта и телефона считает `demand_model.cbm` через `run_workspace.py`. Модель v2 этим файлом не подменяется: у неё другой набор колонок.

## Технологии

| Часть | Стек |
|---|---|
| Сайт | Next.js 15 (App Router), React 19, TypeScript, Tailwind CSS |
| API согласования | Python, FastAPI, uvicorn. Запуск из папки `backend/` |
| Расчёт | pandas, CatBoost. Модель лежит в `ml/models/`, не внутри `backend/` |
| Телефон | Flutter, riverpod, dio. Тот же REST |
| Данные | Шесть Excel из 1С. Схема полей — `docs/06-datasets.md` |

Роли в API: `aigerim` / `buyer` — менеджер закупа, `daniyar` / `director` — руководитель. Пароли для демо такие же, как роль. Утверждать и возвращать заказ может только руководитель.

## Запуск

Нужны Python 3.11+ и Node.js 20+. Модель `ml/models/demand_model.cbm` уже в репозитории.

```bash
pip install -r backend/requirements.txt
cd frontend && npm install
```

Три процесса.

1. Посчитать заказ из выгрузки 1С. Файлы — в `IEK_DATA_DIR` (по умолчанию `/Users/azamatomirtaj/Documents/IEK`): динамика продаж, ежемесячные продажи, ежемесячные остатки, путь, MOQ, сезонность.

```bash
cd backend
python3 run_workspace.py
```

Появится `backend/data/workspace.json`. В git он не коммитится: это результат конкретной выгрузки.

2. API, его вызывает телефон.

```bash
cd backend
uvicorn main:app --host 0.0.0.0 --port 8000
```

Это `backend/main.py`. Файл `api/main.py` — отдельный чат-ассистент, для мобилки он не нужен. Swagger: http://127.0.0.1:8000/docs

3. Сайт.

```bash
cd frontend
npm run dev
```

http://localhost:3000 — дашборд, `/import` загрузка, `/orders` заказы, `/sku/[артикул]` карточка, `/anomalies`, `/suppliers`.

Телефон:

```bash
cd mobile
flutter pub get
flutter run
```

Симулятор iOS ходит на `http://127.0.0.1:8000`, эмулятор Android — на `http://10.0.2.2:8000`. Реальный телефон в той же сети:

```bash
flutter run --dart-define=QOR_API=http://<IP компьютера>:8000
```

Вход руководителя: `daniyar` / `director`.
Сценарий проверки и автотесты телефона — `mobile/README.md`, раздел «Как проверить на телефоне».

## Как проверить

1. `python3 backend/run_workspace.py` завершается без ошибки и пишет число SKU к заказу.
2. `curl -s http://127.0.0.1:8000/health` возвращает `"ready": true` и `"model": "demand_model.cbm"`.
3. На сайте `/orders` есть строки с артикулом, остатком, «в пути», рекомендуемым количеством и бейджем срочности. Раскрытие строки показывает шаги расчёта.
4. Измените количество в файле «Путь» и пересчитайте: рекомендуемое количество по этому артикулу изменится. Так же на результат влияют остаток и история продаж.
5. Войдите в API как `daniyar` и откройте `GET /v1/bundle` — тот же JSON, что на сайте. `POST /v1/orders/iek-current/approve` переводит заказ в `approved`. Повторное утверждение — 409. Тем же методом под `aigerim` — 403.
6. На телефоне тот же заказ: «Утвердить» или «Вернуть» с комментарием меняет статус, который читает `GET /v1/orders/current`. Поставщику запрос не уходит.
7. Выбросы v2: `scripts/prepare_dataset_v2.py` помечает `outlier_flag` и заменяет всплеск медианой. Компенсация пустого склада — колонка `demand_adjusted` в том же скрипте.
