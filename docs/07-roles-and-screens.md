# Роли, экраны и сценарий демо

Сайт и мобилка — **разные сценарии**, не один интерфейс на двух ширинах.
Жюри должно увидеть разделение ролей, а не «адаптив дашборда».

Один бэкенд (FastAPI): расчёт, прогноз, выбросы, LLM. Клиенты только отображают.

---

## Кто где работает

| Клиент | Кто | Что делает | Чего нет |
|---|---|---|---|
| **Сайт** — рабочее место | Менеджер по закупкам за десктопом | Запускает расчёт, правит qty в таблице, смотрит водопад и аномалии, чатится с LLM по SKU, отправляет на согласование, экспортирует в 1С | Утверждение «с телефона» не нужно — это не его сценарий |
| **Мобилка** — контроль на ходу | Менеджер вне офиса + **руководитель** | Смотрит риски и пуши, открывает заказ, спрашивает «почему», утверждает или возвращает с комментарием | Нет больших таблиц, нет правки сетки, нет экспорта в 1С |

Human-in-the-loop кейса закрывается явно: на мобилке шаг **«Утвердить / Вернуть»**. Заказ не уходит поставщику сам.

---

## Дизайн-система (общая, два клиента)

Сделать компонентами до экранов — тогда сайт и мобилка выглядят как один продукт.

| Токен | Значение |
|---|---|
| Фон | `#F5F7FA` |
| Карточка | `#FFFFFF`, радиус 12 (web) / 16 (mobile) |
| Акцент | `#2563EB` |
| Текст | Inter. Заголовок 20–24, тело 14, моно для артикула |
| **Критично** | `#DC2626` фон `#FEF2F2` |
| **Скоро** | `#D97706` фон `#FFFBEB` |
| **Норма** | `#059669` фон `#ECFDF5` |
| **Аномалия** | `#EA580C` фон `#FFF7ED` |
| **Stockout** | красная штриховка на графике |
| Бейдж срочности | Критично / Скоро / Норма — один компонент |
| Строка заказа | артикул · имя · остаток · в пути · рек. qty · бейдж |
| Мини-график | 12 мес. факт + пунктир прогноза |
| Водопад | только сайт: база → сезонность → тренд → stockout+ → аномалия− → в пути− → MOQ |

---

## Сайт — ядро демо (делать первым)

1. **Заказы поставщикам** — запуск расчёта (склад / категория), таблица с inline-правкой qty, группировка по поставщику, «Отправить на согласование».
2. **Карточка артикула** — график (аномалии оранжевые, stockout красный), **водопад расчёта**, обоснование, **чат с LLM**.
3. **Аномалии** — исключённые разовые накладные (из `Динамика продаж`, порог p99 / IQR).
4. **Утверждение + экспорт** — статус «На согласовании / Утверждено / На доработке», Excel/CSV для 1С только после «Утверждено».
5. **Дашборд трендов** — по категориям, если останется время.

Не делать на сайте: пуш-центр, swipe-approve, «главная как у телефона».

## Мобилка — ядро демо (делать вторым)

1. **Главная** — сегодня: N SKU под риском дефицита, M заказов ждут утверждения, сумма.
2. **Уведомления / пуш** — «`MVA20-1-016-C` закончится через 5 дней, срок поставки 14» / «Заказ IEK готов к утверждению».
3. **Заказ поставщика** — список позиций, срочность, итог, **Утвердить** / **Вернуть на доработку** + комментарий. Qty только читается (править — на сайте).
4. **Карточка артикула (лёгкая)** — мини-график, 2–3 предложения обоснования, «Спросить почему» (чат или голос).

Не делать на мобилке: wide-таблица, экспорт 1С, настройки горизонта прогноза, водопад из 7 ступенек.

---

## Порядок дизайна (не расползаться)

1. Дизайн-система: срочность, типографика, бейджи, строка, мини-график.
2. Сайт: заказы + карточка с водопадом.
3. Мобилка: главная + утверждение + макет пуша.
4. Остальное — если останется время.

## Сценарий демо для жюри (2–3 минуты)

1. **Сайт.** Менеджер жмёт «Пересчитать» по складу Алматы / IEK. Таблица: 300+ позиций, часть «Критично».
2. Открывает SKU (напр. `MVA20-1-016-C`). Водопад: база × сезонность 1.22 (июль) + компенсация пустых остатков − исключённая накладная 1 000+ шт.
3. Переходит на «Аномалии», показывает ту самую накладную — в регулярный заказ она не вошла.
4. Жмёт «Отправить на согласование».
5. **Телефон.** Пуш руководителю: «Заказ IEK, 847 позиций, ₸… готов к утверждению».
6. Открывает заказ → «Почему так много?» по строке → ответ LLM про сезонность и stockout.
7. **Утвердить.** На сайте статус → «Утверждено», кнопка «Экспорт в 1С» оживает.

Один бэкенд, два клиента, один статус заказа.

## Мобильный стек (решение команды)

Остаёмся на **Flutter** — человек под мобилку уже есть. UX — согласование, не копия сайта.
Альтернативы Claude (Expo / PWA) не берём, чтобы не плодить стеки.

Расчёт, прогноз, выбросы, LLM — только на сервере. Flutter ходит в тот же REST, что и Next.js.
