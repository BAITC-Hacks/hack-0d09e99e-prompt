## Схемы

### 1. Динамика продаж — транзакции

Поля: `Дата`, `Номер`, `Документ`, `Код`, `Номенклатура`, `Ед.`, `Склад`, `Количество`.

- Дата в формате `ДД.ММ.ГГГГ ЧЧ:ММ:СС`, последняя строка — `Итого` (выкидывать).
- Тип документа почти всегда `Расходная накладная` (171 597). Есть 3 прихода и 3 заказа покупателя.
- Количество: медиана 4, p95 = 96, p99 = 288, p999 = 1 000. **732 строки ≥ 500 шт, 202 строки ≥ 1 000 шт** — это кандидаты в разовые крупные заказы.
- 115 строк с отрицательным количеством (возвраты / сторно) — в регулярный спрос не включать.
- Единицы: шт (87%), м (кабель ITK), упак.
- **Нет обезличенного ID клиента и нет цены.** Крупную продажу «одному клиенту» ловим по размеру накладной (`Номер`) и IQR по SKU, не по клиенту.

### 2. Ежемесячные продажи (wide)

`Номенклатура` | `Номенклатура.Код` | янв. 2024 … сент. 2026 | `Итого`

Две строки шапки (вторая — «Количество»). Последняя строка — `Итого`. Пустая ячейка = не продавали в этом месяце, не ноль.

### 3. Ежемесячные остатки (wide)

`Номенклатура` | `Ед.` | `Номенклатура.Код` | янв. 2024 … сент. 2026 | `Итого`

Три строки шапки (`Количество` / `нач. остаток`).  
Явных нулей в остатках нет: **пустая ячейка = товара не было**. Это наш proxy stockout.

- 27 678 пустых ячеек из 94 182 (29%).
- 2 025 SKU имели хотя бы один «пустой» месяц.
- На сент. 2026 пустой остаток у **797 SKU** — зона риска дефицита прямо сейчас.

### 5. MOQ

`№` | `Код 1с` | `Артикул поставщика` | `Наименование` | `Мин. разр. к отгр.`

Медиана = 1, среднее ≈ 11, макс = 600. Топ значений: 1 (1 239 SKU), 10, 50, 20, 12. Рекомендуемое количество округляем вверх до MOQ.

## Как закрываем must-have кейса этими файлами

| Must-have | Источник | Как |
|---|---|---|
| 1. Базовая потребность + все входы влияют на результат | продажи + остатки + путь + MOQ + сезонность | `need = forecast(horizon) − stock − in_transit`, затем ceil до MOQ. Изменение «в пути» двигает qty |
| 2. Сезонность и устойчивый рост | `Сезонность ИЭК` + monthly sales | бренд-коэф. × SKU seasonal index; рост = наклон 12 мес. после очистки выбросов |
| 3. Компенсация упущенного спроса | monthly stock (NaN) + monthly sales | в месяцы stockout подставляем ожидаемый спрос, не факт 0 |
| 4. Разовые крупные заказы | динамика (`Номер` + qty) | IQR / p99 по SKU и всплеск одной накладной; в регулярный спрос не идёт |
| 5. Список по поставщикам + обоснование | все файлы | поставщик в этих данных один — **IEK**; обоснование собираем из слагаемых формулы |

## Чего в выгрузках нет (и что не выдумываем)

- Обезличенный ID клиента и цена в транзакциях — нет. Не синтезируем клиентов.
- Явный справочник категорий — нет. Группы берём из префикса `Код 1с` / текста номенклатуры, если понадобятся для дашборда.
- Несколько поставщиков — нет, только IEK. UI «по поставщикам» остаётся, но на этих данных одна группа.
- Явная таблица stockout — нет, только proxy через пустые остатки.

## Правила загрузки (для парсера)

1. Не коммитить `.xlsx` в git (коммерческая выгрузка). Читать с диска: `IEK_DATA_DIR` (по умолчанию `/Users/azamatomirtaj/Documents/IEK`).
2. Выкидывать строки `Итого` и служебные шапки 1С (2–3 первые строки в wide-отчётах).
3. Ключ = `Код 1с` как строка, хвостовое `_` сохранять (`200400085_`).
4. Wide-таблицы плавить в long: `(sku, month, value)`.
5. Колонки «в пути» парсить регекспом: номер УТ + дата документа + ETA.
6. Количество в динамике: в спрос идут только `Расходная накладная` с qty > 0.
